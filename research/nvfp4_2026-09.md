# NVFP4 checkpoints, September 2026 sweep — every model measured

**Purpose:** `research/nvfp4.md` (2026-07) priced NVFP4 arms for four models; the
per-model notes for DeepSeek-V4-Flash, Qwen3.8-Flash-Next and GLM-5.3-Flash
recorded that no official checkpoint existed. The owner asked for a re-sweep (2026-09-06).
Result: **every model now has a measured NVFP4 arm** except GLM-5.3 (the
744B model), which keeps NVIDIA's 5.2 recipe as a projection. Also
checked: whether FP8 KV is servable on every model — see § 4.

## 1. Method

For each candidate repo, every safetensors shard header was read with HTTP
range requests (8-byte length prefix, then the JSON header) and every
tensor's bytes summed from dtype × shape; tensors were binned by name into
routed experts, shared experts, MTP, embed, lm_head, n-gram table, vision,
and the rest. The method was validated on the FP8 bases first: for
Qwen3.8-Flash-Next it reproduces `w_route_total` (120,810,700,800 B) and the
4,915,800 B/expert figure exactly, and the always-active sum within 0.8%
(the PLE projection is binned differently). NVFP4 ledgers therefore use the
FP8 constants' own convention: the always-active read is the FP8 constant
plus the measured delta on the same tensors; expert bytes are the measured
per-expert figure × experts-per-token (or total experts) × decode layers.

"Official" here means NVIDIA, the vendor, or RedHatAI — the bar the study
already used for the 35B-A3B. Community conversions (unsloth, RadixArk,
QUASAR, …) were listed but not priced.

## 3. What the numbers mean for the frontier

- Qwen3.8-Flash-Next and GLM-5.3-Flash: expert reads shrink 1.78×, so the
  high-concurrency decode point moves up; GLM-5.3-Flash's fixed read grows
  20% (the BF16 upcast), so low-concurrency decode slows — the trade
  `research/nvfp4.md` § 6.1 described for the 35B-A3B, now measured on a
  second recipe.
- DeepSeek-V4-Flash: the NVFP4 arm is **heavier** than the native checkpoint
  on every expert byte and identical elsewhere. Selecting NVFP4 for it
  should read as "the NVFP4 kernel path", not "smaller weights"; the
  explorer prices what the checkpoint weighs and the table tags the row.
- Qwen3.8-27B: 24% fewer resident bytes than FP8 (30.87e9 → 23.42e9).

## 4. FP8 KV: who can serve it

Checked against the vLLM recipes on 2026-09-06 (GLM-5.3-Flash's recipe
last updated 2026-09-05):

| Model | FP8 KV | Note |
|---|---|---|
| Qwen3.8-27B, Qwen3.6-35B-A3B, Mistral-Medium-3.5 | yes, the study default | — |
| GLM-5.3 | **required** (DSA path asserts a quantized cache) | `kv_fp16_ok: false` |
| DeepSeek-V4-Flash-0731 | **required** on the main KV | `kv_fp16_ok: false` |
| Qwen3.8-Flash-Next | yes | no fp8-KV assert on the QSA path |
| GLM-5.3-Flash | **Blackwell only** — "Hopper does not support FP8 KV cache for this model; Hopper runs BF16 KV" | `kv_fp8_blackwell_only: true` stays; H200 rows keep pricing BF16 KV |

So every model supports FP8 KV on Blackwell; on Hopper every model but
GLM-5.3-Flash does. Nothing in the KV rules changed.
